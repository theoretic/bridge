## Who loads the UIkit layer

Only davinci, on the 55 screens that print the legacy stack. The one reason on each of them is
`Script:app/modules/RockMigrations/RockMigrations.js`: RockMigrations adds that jQuery script to
every admin page, and it calls `UIkit.tooltip` (its field hints) and `UIkit.notification` (shift-
click copy) without checking for UIkit. Where the stack prints, the script runs, so the layer is
right. `uikit-allow.txt` allows it by reason (`reason:Script:*/RockMigrations/RockMigrations.js`),
so another module that starts loading the layer on those screens would still be reported.

The first run of the day found 169 of davinci's 172 screens with the layer, 169 unexpected: the
script counted also where it is deferred with the stack, not printed, so it does not run. Fixed in
0.26.0 (`isDeferredScript()`, ADR 0017 addendum "deferred scripts"). RockMigrations' own config
screen also printed `uk-table-striped`, now in the compat file.

None from the other UIkit-using modules on these sites:

- Fluency (davinci, livingston, txm): `uk-select` covered, `uk-tooltip` no reason.
- PageTableNext (atispro): rows and button row covered, the row icons drawn (0.26.0 C1, C2).
- AgentTools (atispro v21, livingston v39, txm): no screen loads the layer. atispro's Process
  screen (`setup/agent-tools/`) has no uncovered markup; livingston's has no Process page. The
  PageEngineer field (`uk-grid`, `uk-toggle`), which would still load it by design, renders on no
  screen of this suite.
- AdminPageTool (livingston, ofsla), AdminPageDealers (paraavis): pager, tables and button groups
  covered (0.26.0 C1).
